# VirtualBox 7.2.6 Windows：VirtIO-GPU/Venus 开发计划

## 1. 目标与验收口径

目标是交付一个可在 Windows 宿主机运行的 VirtualBox 版本，使 Linux 客户机能够通过 VirtIO-GPU 使用宿主机 GPU 完成图形和 Vulkan 工作负载，并且有可重复的性能测试结果。

本项目不做 PCIe 显卡直通，也不要求宿主机有第二块显卡。客户机通过 VirtIO-GPU 暴露的 Venus 协议提交 Vulkan 命令，VirtualBox 在宿主机使用 Windows Vulkan loader 和厂商 ICD 执行这些命令，从而共享当前宿主机 GPU。

## 3. 总体架构

```text
Linux guest Vulkan app
        │
Mesa Vulkan Venus / virtio-gpu driver
        │  virtqueue + blob/resource commands
        ▼
VirtualBox DevVirtioGPU (R3)
        │
共享内存、eventfd 等效通知、资源生命周期、同步/ fence
        ▼
Host GPU backend
        │
Windows Vulkan loader + vendor ICD
        ▼
宿主机 NVIDIA / AMD / Intel GPU
```

实现时保留现有 VMSVGA/D3D11 作为显示兼容路径。这里的“Vulkan 接口转发”不是逐个代理客户机的 Vulkan ABI，而是转发 Venus/virtio-gpu 的资源、命令缓冲、同步对象和 fence；这样可以减少 API 往返并保留宿主机驱动的批处理能力。

## 4. 分阶段开发计划

### P0：可重复的 Windows 基线构建（1 周）

工作内容：

- 固定 Windows 11 x64、Visual Studio 2019/2022 工具链版本、Windows 10 SDK/WDK 版本和依赖目录。
- 在 `VirtualBox-7.2.6` 目录运行 `configure.vbs`，生成独立的 Windows amd64 `AutoConfig.kmk`；不要覆盖现有 Linux 配置。
- 先关闭文档、Java、Python、Qt、扩展包等非必要组件，缩短第一次构建时间；保留 VBoxManage、VBoxHeadless、核心设备和 Guest Additions 所需组件。
- 生成 `out\win.amd64\release` 构建树，先编译 `VBoxRT`、`VBoxVMM`、`VBoxDD`、`VBoxSVC`、`VBoxHeadless`，再编译 GUI 和打包目标。

建议的首轮命令（在 `VirtualBox-7.2.6` 根目录执行；路径按实际工具安装位置替换）：

```bat
cscript //nologo configure.vbs --target-arch=amd64 --with-kBuild=D:\tools\kBuild
call kBuild\envwin.cmd --win64 --release kmk -j8 quick
call kBuild\envwin.cmd --win64 --release kmk -j8 all
```

`quick` 用于快速验证运行所需核心目标，`all` 用于完整构建。每次重新运行 `configure.vbs` 都会重写 `AutoConfig.kmk`，所以 Windows 和 Linux 必须使用不同 checkout 或在切换后重新保存配置文件。

阶段出口：

- 产生 `VirtualBox.exe`、`VBoxHeadless.exe`、`VBoxManage.exe`、`VBoxDD.dll`、`VBoxVMM.dll`。
- 在隔离目录启动 `VBoxManage list hostinfo`，创建并启动一个无 3D 的 Linux VM。
- 保存完整 configure/build 日志和工具链版本；任何失败都记录第一条 `FAILED`、`fatal error` 或 `LNK`。

### P1：VirtIO-GPU 最小设备（2 周）

工作内容：

- 新增 `src/VBox/Devices/VirtIO/DevVirtioGPU.{h,cpp}`，复用 VirtIO core 的 PCI transport、feature negotiation、virtqueue 和中断机制。
- 在 `src/VBox/Devices/Makefile.kmk`、`src/VBox/Devices/build/VBoxDD.h`、`VBoxDD.cpp` 增加源文件、设备声明和注册。
- 实现 VirtIO 1.0 基本配置空间、2D control queue、cursor/scanout、resource create/attach/transfer/flush 和 fence 错误处理。
- 在 Main API/XML 增加显式设备类型和版本检查；旧 VM 配置必须继续走 VMSVGA。
- 先做 software/CPU backend，把 guest 提交的资源和 scanout 正确显示出来，建立协议正确性基线。

阶段出口：

- Linux 客户机识别 `virtio-gpu-pci`，能启动桌面并完成分辨率切换、热重置、暂停/恢复。
- virtio-gpu 基础测试通过，错误 queue descriptor 不会导致 VBoxHeadless 崩溃。
- 与 VMSVGA 的同分辨率截图逐像素或按允许色差比较。

### P2：Windows 宿主机 Vulkan/Venus 通路（3–5 周）

工作内容：

- 选定并锁定 Mesa Venus 协议版本，以及宿主机依赖：Vulkan loader、Windows vendor ICD、`virglrenderer`/对应 Venus host 实现和必要 SPIR-V 工具。
- 在 VirtualBox R3 中建立 host backend 抽象：instance/device/queue、memory import/export、fence/semaphore、command submission、resource/blob 映射。
- 建立协议到 Vulkan 的固定映射：guest resource/blob → `VkBuffer`/`VkImage`，command stream → `VkCommandBuffer`，guest fence → `VkFence`/timeline semaphore；禁止在 backend 中混入 VM 配置或显示逻辑。
- Windows 句柄使用 NT handle/D3D/Vulkan 外部内存能力时，先做能力探测；不支持的扩展必须在 guest feature negotiation 阶段明确拒绝。
- 处理线程模型：virtqueue 消费线程、Vulkan submission 线程、显示线程分离；使用有界队列和 fence 回收，避免 guest 无限占用 host GPU。
- 增加 host capability 查询和日志：GPU 名称、Vulkan API 版本、扩展、显存预算、是否 zero-copy、fallback 原因。

阶段出口：

- Linux 客户机 Venus 驱动能创建 Vulkan device，运行 `vulkaninfo` 和最小三角形/compute 样例。
- 所有 Vulkan 资源都有明确的创建、引用计数、同步、销毁路径；VM reset 后无句柄泄漏。
- 不支持 Vulkan 的主机回退到 P1 2D 显示，并向用户报告原因。

### P3：性能和稳定性（2–3 周）

工作内容：

- 建立固定测试矩阵：1080p/4K、窗口/全屏、OpenGL/Vulkan、图形/compute、单 VM/多 VM、冷启动/热重置。
- 采集端到端帧延迟、FPS、CPU 占用、GPU 利用率、显存占用、virtqueue 吞吐、fence 等待时间和崩溃率。
- 优先优化批量提交、持久映射、资源复用、异步 transfer、scanout zero-copy；每项优化必须有前后数据。
- 使用 Windows GPUView/ETW、Vulkan validation layer、VirtualBox release log 和客户机 `dmesg` 对齐时间线。
- 增加 fuzz/负向测试：畸形 descriptor、超大 resource、错误 fence、guest reset、宿主机驱动重启。

阶段出口：

- 在指定硬件上达到预先约定的基线，例如 1080p Vulkan 样例不低于 VMSVGA 3D 的 2 倍，端到端帧延迟和 CPU 占用有测量记录。
- 连续 8 小时图形压力测试无崩溃、无显存持续增长；暂停/恢复和 VM 重启通过。

## 6. 配置和兼容策略

- 新增明确的 `VBOX_WITH_VIRTIO_GPU`、`VBOX_WITH_VIRTIO_GPU_VENUS`、`VBOX_WITH_VIRTIO_GPU_VULKAN` 开关，默认先关闭 Venus，避免影响普通构建。
- VM 配置建议增加 `--graphics-controller virtio-gpu` 和 `--gpu-backend auto|venus|software`；`auto` 按 host capability 选择，禁止静默切到低性能路径。
- 当前实现同时支持机器/全局 ExtraData `VBoxInternal/Devices/virtio-gpu/0/Config/Backend` 和 `VBoxManage modifyvm --gpu-backend auto|venus|software`，由设备 CFGM 注入 backend；后续仍需在真实 VM 启动路径验证配置传递。
- 维护三种模式：`vmsvga`（现有兼容）、`virtio-gpu-2d`（P1）、`virtio-gpu-venus`（P2/P3）。
- 迁移和保存状态必须记录 backend、协议版本、资源格式和 host capability；不兼容时在恢复前报错。

## 7. 风险与决策点

| 风险 | 影响 | 处理 |
|---|---|---|
| Windows host 端 Venus 依赖难以稳定集成 | P2 延期 | 先交付 P1；锁定 Mesa/Vulkan 版本并做独立 DLL smoke test |
| VirtualBox ring-3/ring-0 边界和 saved state 复杂 | reset/迁移崩溃 | 先完成 CPU backend 与 reset/fuzz，再接 Vulkan |
| 宿主机 Vulkan 扩展或外部内存能力不足 | zero-copy 不可用 | 回退到 host copy，并记录实际性能；不宣称 zero-copy |

## 8. 第一批实际任务（建议立即执行）

1. 准备 Windows 构建机并记录 `cl.exe`、Windows SDK/WDK、Python、yasm/nasm、kBuild 版本。
2. 从 Linux checkout 分离出 Windows 构建目录，运行 `configure.vbs --target-arch=amd64`，生成并保存 `configure.log`。
3. 编译未经修改的 VirtualBox Windows amd64 基线，确认 VBoxHeadless 能启动无 3D Linux VM。
4. 建立 `DevVirtioGPU` 空设备骨架，只完成设备注册、feature negotiation 和空队列错误处理，先让构建和设备枚举稳定。
5. 决定客户机基线镜像（建议 Ubuntu 24.04 或 Fedora 对应 Mesa 版本），固定内核、Mesa、Vulkan tools 和测试样例。
6. 在 P1 结束前不要接入 Vulkan；不要把 VMSVGA 3D 的成功误报成 Venus 转发成功。

## 9. 完成定义

项目只有在以下证据齐全时才算完成：

- Windows 安装包和可复现构建脚本；
- Linux 客户机识别 VirtIO-GPU，Vulkan device 创建成功；
- host GPU 名称、Vulkan ICD 和 backend 选择可在日志中核对；
- Vulkan smoke、reset、暂停/恢复、长时间压力测试通过；
- 性能报告包含同输入、同分辨率、同客户机镜像下的对比数据；
- 明确记录 Venus 协议版本、宿主机 Vulkan ICD、实际 backend，以及发生回退时的原因。
