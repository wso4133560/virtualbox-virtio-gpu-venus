## 本次设备改动

- 使用已有 VirtIO PCI transport，设备名 `virtio-gpu`，PCI ID `1af4:1050`，非 VGA 显示类，GPU device type 16。
- 仅在 R3 运行；新开关 `VBOX_WITH_VIRTIO_GPU` 默认关闭，通过构建脚本 `-EnableVirtioGpu` 开启。
- 配置区为 16 字节，包含 `events_read`、`events_clear`、`num_scanouts`、`num_capsets`。目前报告一个未连接的 scanout，capset 数为 0。
- 两条队列：control 和 cursor。`GET_DISPLAY_INFO` 返回 16 个禁用的显示项；不支持的控制命令返回错误。cursor 只归还描述符，目前不创建或移动光标。
- 完整请求携带 fence 时保留 fence ID；不回显未提供的扩展标志和保留字段。短请求、返回缓冲不足与空完成都有确定的完成路径。
- 新增保存/恢复与设备重置入口；2D 资源、背板描述符、像素缓冲和 scanout 状态纳入保存状态，并校验尺寸、地址范围和背板总量。
- saved state 版本已升为 6，记录请求的 `Backend` 选择和 `auto` 解析后的实际 backend；恢复时要求两者一致，避免软件/Venus 路径互相恢复。
- 2D 路径支持 B8G8R8X8 资源的创建/释放、背板挂接/解绑、客户机内存到主机像素缓冲的 transfer、scanout 绑定和 flush 序号；启用 Vulkan image 时，scanout flush 会先把 device-local image 回读到软件像素影子，再调用显示连接器更新区域；尚未接入 VMSVGA/窗口显示。
- Main API 图形控制器枚举新增 `VirtioGPU`，设置文件接受并保存 `VirtioGPU`，x86 客户机配置阶段会插入 `virtio-gpu` PCI 设备节点；此路径已完成编译验证，尚未完成真实 VM 启动验证。
- Virtio-GPU 设备支持 `Backend=auto|software|venus`：`auto` 在宿主 Vulkan 探测失败时回退软件路径，`software` 显式禁用 Vulkan，`venus` 探测失败时拒绝构造设备；Main 配置从机器或全局 ExtraData `VBoxInternal/Devices/virtio-gpu/0/Config/Backend` 注入该值，避免无提示地切换到低性能后端。
- 设备现在声明标准 `RESOURCE_BLOB` 和 `CONTEXT_INIT` feature bit，使 Linux virtio-gpu 驱动能够协商现代资源/上下文路径；Venus capset 仍保持未发布，避免把不完整命令集误报为完整 Vulkan 支持。
- 配置示例：`VBoxManage setextradata "<VM名称>" "VBoxInternal/Devices/virtio-gpu/0/Config/Backend" venus`；该设置只在选择 `VirtioGPU` 控制器的 VM 上生效。
- 软件显示连接器已接入：scanout 设置调用 `PDMIDISPLAYCONNECTOR::pfnResize`，flush 调用 `pfnUpdateRect`；当前没有真实 VM 显示端到端证据。
- `-EnableVirtioGpuVenus` 构建开关已加入；启用后 R3 通过系统目录加载 `vulkan-1.dll` 并检查 `vkGetInstanceProcAddr`，失败时记录并保留软件路径。该探测不等于 Venus 协议执行，也不代表已创建 Vulkan device。
- Venus 探测现在会创建 Vulkan instance、枚举物理设备，选择同时支持图形和计算的 queue family，创建 Vulkan device 并取得 queue，销毁路径已覆盖；这仍不等于 Venus 命令转发或客户机 Vulkan device 创建。
- Vulkan 初始化会枚举所选物理设备的 `VK_KHR_external_memory`/`VK_KHR_external_memory_win32` 与 `VK_KHR_external_semaphore`/`VK_KHR_external_semaphore_win32` 扩展并写入宿主日志，作为后续 Windows 句柄共享和 zero-copy 设计的能力边界；当前只探测，不启用扩展或导入客户机句柄。
- 测试路径会在该 queue 上向 VirtIO-GPU host-visible resource 提交 `vkCmdFillBuffer`，等待 fence 后从映射内存回读固定值；该证据证明资源上的宿主 Vulkan 命令确实执行，不代表客户机命令已经转发。
- 初始化同时查询 `VkPhysicalDeviceMemoryProperties`，记录 memory type 数量和 device-local heap 容量，为后续 blob/resource 内存选择提供能力边界；尚未实现客户机内存导入或 zero-copy。
- 启用 Venus 构建时，2D resource 会创建 host-visible Vulkan buffer，并尝试创建 device-local `VkImage`；transfer-to-host-2D 会用持久 command buffer 执行 buffer→image 上传，绑定 scanout 的 resource flush 会执行 image→buffer 回读后更新显示连接器。资源释放、reset 和 saved-state 恢复路径会清理或重建这些资源。这仍不是外部句柄共享，也不代表客户机 blob/image 命令已完成。
- 已加入 `RESOURCE_CREATE_BLOB` 的 32 字节 body 解码，校验 blob 大小、4 字节对齐、backing 数量和地址溢出，并复用 host-visible Vulkan buffer 生命周期；尚未向客户机发布 capset，因此不会误报完整 Venus 能力。
- 已加入 `CTX_CREATE`/`CTX_DESTROY`，限制 64 个上下文，校验 context ID、名称长度和重复创建，并把上下文纳入 saved state；上下文目前还没有关联 Vulkan command stream。
- 已加入 `CTX_ATTACH_RESOURCE`/`CTX_DETACH_RESOURCE`，每个上下文最多绑定 64 个资源；资源释放会自动解除绑定，保存状态会校验资源存在性和重复 ID。
- 已加入 `SUBMIT_3D` 入口：校验 context、命令长度（上限 1 MiB）和关联资源；当前可解码 Mesa Venus 的 44 字节 `vkCmdFillBuffer`、`vkCmdUpdateBuffer`，真实编码的 `44 + 24×regionCount` 字节 `vkCmdCopyBuffer`（最多 256 个 region），84 字节 `vkCmdClearColorImage`（单个完整 color subresource range），104 字节 `vkCmdCopyBufferToImage` 和 104 字节 `vkCmdCopyImageToBuffer`（均为单个完整 2D color region），120 字节 `vkCmdCopyImage`（两个完整 2D color image 的单个 region），以及 128 字节 `vkCmdPipelineBarrier`（单个完整 color image barrier），映射 VirtIO-GPU resource 并在宿主 queue 执行，写入 image-backed resource 后同步 device-local image，其他非空命令仍返回 `ERR_UNSPEC`。
- 已加入 `GET_CAPSET_INFO`/`GET_CAPSET` 的响应结构和边界处理；当前 `num_capsets=0`，查询明确返回无效参数，不向客户机伪造 Venus 能力。
- 公共 VirtIO core 支持显式队列数量，现有调用默认维持原来的 24 队列上限；修复 16 位索引回绕，拒绝循环链、越界索引、未协商的间接描述符、地址/长度溢出；过滤空段并传播返回数据的内存写失败。

协议结构对照来源：[Linux v6.18 官方 virtio_gpu.h](https://github.com/torvalds/linux/blob/v6.18/include/uapi/linux/virtio_gpu.h)。目前没有宣称完整 VirtIO-GPU 规范一致性，也没有宣称提供 virgl 或 Venus capset。

## 复现

从仓库根目录运行，使用 PowerShell 7、VS2022 和已准备好的 SDK/WDK/YASM：

```powershell
./tools/build-windows.ps1 -WithoutHardening -EnableVirtioGpu -EnableVirtioGpuVenus -Targets @('VBoxDD','tstVirtioGPU') -Jobs 12
./tools/test-virtio-gpu.ps1
./tools/test-windows-baseline.ps1
```

多目标需要 PowerShell 数组写法，不能用空格分隔的裸参数代替。构建脚本的配置阶段读取本机 WMI 注册表；受限执行环境可能需要允许这项本机读取。测试脚本本身不安装驱动、不注册服务、不启动 VM。

测试程序直接编译生产 `VirtioCore.cpp` 和 `DevVirtioGPU.cpp`，通过有界 RAM 与 PDM 内存/中断回调测试真实解析和完成逻辑。保存状态使用内存中的 SSM 读写端点。最后一组测试加载实际生成的 `VBoxDD.dll` 并调用其注册入口，确认 GPU 设备确实位于交付模块内。

覆盖的 21 组测试（第 9 组包含 image 上传、回读、跨资源 copy 及重建后的 image 同步检查；第 13 组包含 image/barrier/copy-image 命令序列化边界）：

1. Windows 宿主 Vulkan loader 和 `vkGetInstanceProcAddr` 探测。
2. Vulkan instance、物理设备、device 和图形/计算 queue 创建探测。
3. 宿主 Vulkan queue 命令提交、fence 等待和回读验证。
4. 后端选择 `auto`/`software`/`venus` 与非法值边界。
5. 线格式、只读配置和事件清除。
6. 队列数量和未实现的队列。
7. 显示信息响应、fence 与保留字段。
8. capset 查询边界和未发布的能力集合。
9. 2D 资源、device-local `VkImage`、背板传输、scanout/flush 回读、image-backed fill、跨资源 image copy、资源重建和资源释放。
10. blob 资源创建、backing 校验、host Vulkan buffer 和资源释放。
11. host-visible 资源上的 Vulkan `vkCmdFillBuffer` 提交、fence 等待和映射回读。
12. 持久命令池、命令缓冲和 fence 的 8 条填充命令批量提交吞吐测量。
13. Venus `vkCmdFillBuffer` 44 字节、`vkCmdClearColorImage` 84 字节、`vkCmdCopyBufferToImage`、`vkCmdCopyImageToBuffer` 104 字节、`vkCmdCopyImage` 120 字节及 `vkCmdPipelineBarrier` 128 字节序列化解码边界和 flags 校验。
14. context 创建/销毁、重复 ID 拒绝、资源绑定，以及 update/fill/多 region copy 提交和保存状态恢复。
15. 短包、不足的返回空间、未知命令和不支持的标志。
16. cursor 空完成和 65535→0 索引回绕。
17. 循环描述符触发重置需求，重置后恢复处理。
18. 越界头/链索引、间接描述符、地址及总长度溢出。
19. 跨描述符请求/响应、空段和内存读写失败。
20. 保存/恢复活动 image 资源和待处理队列，拒绝错误版本和截断状态。
21. 从生成的 VBoxDD.dll 枚举设备注册。

`test-windows-baseline.ps1` 的版本、headless 帮助、XML 与事件信号量 4 项检查也通过。它们不证明客户机启动、显示或 GPU 执行。

另外使用未定义 `VBOX_WITH_VIRTIO_GPU_VENUS` 的构建配置编译 `VBoxC`、`VBoxDD` 和 `tstVirtioGPU`，并运行同一测试程序通过；这确认 `software` 后端在没有 Venus 编译开关时仍可用。
